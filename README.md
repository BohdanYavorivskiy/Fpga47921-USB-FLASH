# USB LED Control

USB LED controller for the device with VID:PID `1209:0001`.

## FPGA design

The USB device is implemented in the ForgeFPGA project
`usb-to-flash/usb-to-flash.ffpga` (sources in `usb-to-flash/ffpga/src`).
It is a USB Full-Speed device clocked at 48 MHz (PLL0 from the 50 MHz
oscillator). EP0 handles standard control requests; EP1 is a vendor bulk
endpoint carrying the LED and SPI commands.

### USB-SPI bridge

A minimal SPI master (`src/spi_master.v`) is driven from EP1. SPI Mode 0,
8-bit MSB-first frames; MOSI changes on falling SCK, MISO is sampled on rising
SCK. CS# is controlled explicitly by the host (the USB round trip provides all
CS setup/hold time).

| Opcode | OUT payload | IN response | Meaning |
|---|---|---|---|
| `0x10` | 1 byte (TX) | `{0x10, status, rx}` | Shift one byte; `rx` is the byte read from MISO |
| `0x11` | `0` or `1` | `{0x11, status}` | `1` asserts CS# (low), `0` releases it |
| `0x12` | `1..15` | `{0x12, status}` | SCK = 48 MHz / (2 x divider); reset value 1 (24 MHz) |

Status: `0` ok, `1` busy / bad value, `2` unknown opcode, `3` bad length
(transfer), `4` transfer attempted with CS# not asserted. The `0x10` response
is queued when the byte finishes; an IN token before that is NAKed. CS# and
the divider reset to idle/1 on USB bus reset.

Top-level ports (same names as the earlier SPI build): `spi_cs`, `spi_cs_oe`,
`spi_clk`, `spi_clk_oe`, `spi_miso_i`, `spi_mosi`, `spi_mosi_oe`. They are
mapped in the IO Planner to GPIO0 CS#, GPIO1 SCK, GPIO2 MISO, and GPIO3 MOSI.
One USB round trip per byte limits throughput to hundreds of bytes per second,
which suits register access and ID reads, not bulk flash programming.

### LED behaviour

- The LED lights while USB transfers happen: every transaction addressed to
  the device (`led_ctrl` input `act`) keeps it on for about 20 ms after the
  last one (`ACT_TICKS`). SOF packets do not count.
- `LED_SET` (`0x01`, 2-byte argument) now forces the LED on while the argument
  is non-zero and releases it when zero; `LED_OFF` (`0x02`) releases it. The
  millisecond timer was removed to save area, so a timed pulse is no longer
  generated by the FPGA.
- After reset the LED blinks five times (`BOOT_BLINKS` of `btn_led`, `0`
  disables it); the button blinks it twice.

### Area work

- **Placed entirely in TILE00.** The constraint file
  `usb-to-flash/ffpga/placement-constraints/tile00.pdc` pins all logic to
  `chip_tile_x=0, chip_tile_y=0` (cells 0-31 in both axes). The tile holds 140
  CLBs.
- `led_ctrl` provides the shared time base as a 16-bit LFSR (1.365 ms tick, no
  carry chain) instead of a 16-bit counter plus a 16-bit down counter.
  `btn_led` uses that tick (4- and 8-bit counters): about 11 ms debounce and
  175 ms per LED phase.
- `usb_dev` drops duplicate registers and the 16-bit LED value register, and
  stores only the setup-packet bits that are decoded. The SPI TX byte reuses
  the received command byte instead of a separate register.
- `btn_led` has a new input `tick`; its parameters are `DEB_BITS`, `DEB_INIT`,
  `PH_BITS`, `PH_INIT`, `BOOT_BLINKS`.

### Results (synthesis + place and route)

Measured on the previous revision (LED/USB only, before the SPI bridge and the
LED rework):

| Metric | Original | Trimmed |
|---|---|---|
| CLBs | 147 | 127 (tile limit 140) |
| LUT5 | 666 | 619 |
| Flip-flops | 396 | 355 |
| Timing at 48 MHz (WNS) | +2.9 ns | +4.9 ns |

The current revision (SPI bridge + LED activity + LFSR time base) was
synthesized and placed and routed in GPD:

| Metric | Current result |
|---|---:|
| CLBs | 127 (limit 140) |
| TILE00 placement-group usage | 134/140, including 7 carry-chain slots |
| LUT5 | 619 |
| Flip-flops | 355 |
| WNS at 48 MHz (20.833 ns) | +4.514 ns |
| TNS | 0 |

The region report places all 127 instances in `tile00_grp`, with no region
violations. PnR completed with 0 errors and 4 warnings: `spi_cs` and `led` were
not packed with IOB flip-flops, `usb_dp_oe` could not be packed due to FF
control contention, and `i_clk` is fed without a CLKBUF as intended by
`clkbuf_inhibit`.

### Simulation

RTL testbenches are in `usb-to-flash/ffpga/sim`:

```bash
cd usb-to-flash/ffpga/sim
iverilog -g2005 -o /tmp/blink.vvp tb_blink_tb.vt ../src/*.v && vvp /tmp/blink.vvp
iverilog -g2005 -o /tmp/usb.vvp tb_usb_tb.vt ../src/*.v && vvp /tmp/usb.vvp
```

Both print `PASS`. `tb_usb_tb` covers enumeration, the LED activity indicator,
`LED_SET`/`LED_OFF`, and the SPI commands against a Mode 0 slave model
(MOSI/MISO data, 8 clocks per byte, CS# handling, divider limits). It
disables the power-up blinks and shortens the activity stretch with
`defparam`. Full-chip simulation and on-hardware testing have not been run.

## Run

Set up the project's virtual environment and install dependencies:

```bash
./setup_venv.sh
```

The script checks that Tkinter is available. If it is missing, it prints the
platform-specific installation guidance. On macOS with Homebrew Python, it
suggests the matching `python-tk` package.

Launch the graphical interface:

```bash
.venv/bin/python usb.py
```

The window lets you set the LED duration in milliseconds (timed on the host),
leave it on indefinitely, or turn it off. The FPGA's `LED_SET` command itself
only forces the LED on or releases it; it does not implement a duration timer.
CLI operation is also available:

```bash
.venv/bin/python usb.py on 1000
.venv/bin/python usb.py on
.venv/bin/python usb.py off
```

## Build a macOS app

With the dependencies and Tk support installed, run:

```bash
cd packaging
../.venv/bin/python -m PyInstaller --noconfirm --clean --windowed \
  --name "USB LED Control" \
  --osx-bundle-identifier com.bohdanyavorivskiy.usbledcontrol \
  --distpath ../dist \
  --workpath ../build/pyinstaller \
  --specpath . \
  --add-data ../usb.py:. \
  --hidden-import usb.core \
  --hidden-import usb.util \
  --hidden-import tkinter \
  --hidden-import tkinter.ttk \
  --hidden-import tkinter.messagebox \
  launcher.py
```

The app bundle is created at `../dist/USB LED Control.app` (the repository's
`dist` directory). This builds for the architecture and Python version of the
machine doing the build; it is not code-signed or notarized.
